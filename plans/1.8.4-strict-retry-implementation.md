# Human Hindsight 1.8.4: implementation and release plan

Prepared November 11, 2026. **Status: implementation complete; release verification underway.**

Target release: **1.8.4**, following the user's version preference and the project's existing 1.8.x release pattern. This document was originally approved as a plan; the user subsequently authorized implementation, verification, Git staging, PR merge, package publication, and release. The sections below preserve the implementation contract. Release evidence belongs in the PR, CI runs, and published tag.

The user approved a **900-second base timeout** and retaining the **400,000-character default input budget**. An explicit `--input-budget=600000` remains available. The new retry behavior must prevent a recovered digest from triggering reclustering or regeneration of successful prompts.

The reviewed baseline is `main` at `c106c9207c51df0e331ef3532860244177246f7c`, version 1.8.3. The release review observed both npm packages at 1.8.3 and a successful corresponding GitHub release. Recheck remote state before execution; these observations are not a reservation of version 1.8.4.

**1. Release outcome**

A user whose distillation partially failed can preview and retry the recorded unsuccessful work:

```sh
npx human-hindsight@1.8.4 distill --retry-failed --dry-run
npx human-hindsight@1.8.4 distill --retry-failed
```

For authoring failures only:

```sh
npx human-hindsight@1.8.4 distill \
  --retry-failed --retry-stage=author \
  --input-budget=600000 --concurrency=3
```

The first command previews. The second and third retain the normal model-spending consent gate. These are proposed commands, available only after the implementation and publication described below.

The core contract is about **which operations may spend**, not merely whether the ordinary cache happens to match. Successful operations remain excluded even when the retry changes model, timeout, or budget. Existing task grouping remains untouched.

Ship these capabilities together:

| Capability | Required behavior |
| --- | --- |
| Strict recorded retry | `--retry-failed` selects recorded failures, interrupted attempts, and recorded blockers that are now resolved. |
| Stage selection | `--retry-stage=author`, `digest`, `cluster`, or `all`; default `all`. |
| Existing-run recovery | `--recover-tasks=<comma-separated-slugs>` authorizes only named saved tasks from an older run without a failure ledger. |
| Durable progress | Record dispatch intent and validated results so a restart can recover local results without buying them again. |
| Cluster window checkpoints | Preserve successful window results individually, rather than losing them when a later window fails. |
| Honest preview | Display exact selected operation identities, exclusions, local repairs, and remaining blockers. |
| Timeout | Raise the common base to 900 seconds; preserve existing scaling for aggregate operations. |
| Budget | Retain 400,000 characters by default, with explicit overrides and existing truncation disclosure. |
| Compatibility | Keep existing library paths, human edits, reviews, commands, and ordinary refresh behavior. |
| Delivery | Publish matching `human-hindsight@1.8.4` and `cc-hindsight@1.8.4`, then verify actual installed behavior. |

**2. What the current implementation does**

These findings explain where the change belongs:

- `src/commands/distill.ts` always orchestrates digest, cluster, then author. A successful digest retry can change the clustering inputs.
- `src/core/fingerprint.ts` includes model, runner, prompt/schema versions, and inputs in cache lineage. This remains correct for an ordinary refresh.
- `src/distill/pipeline.ts` saves successful digests and the final grouping. Failure reports are primarily transient return values and terminal text.
- Windowed clustering holds successful window results in memory until the whole grouping is saved.
- Authoring writes the Markdown and provenance as separate writes. A crash between them needs recoverable publication.
- `src/claude/consent.ts` currently describes a digest count, a clustering count, and an author estimate. It does not describe an immutable strict retry selection.
- `src/commands/status.ts` can report authored, skipped, and pending work, but cannot reliably distinguish a previous failure from work never attempted.
- `src/runners/shared.ts` supplies the 300,000 ms base timeout to all four adapters.

Relevant existing tests are in `test/pipeline.test.ts`, `test/cluster.test.ts`, `test/author.test.ts`, `test/consent.test.ts`, `test/budget.test.ts`, `test/next.test.ts`, and the runner tests. Keep their ordinary-refresh and human-edit protections.

**3. Invariants that define completion**

1. Strict retry never writes, replaces, deletes, or regenerates `distill/tasks.json`. This also applies when that file is absent.
2. Completing a failed digest never schedules clustering, merging, or authoring.
3. Completing a failed clustering window never schedules a queued window, a new merge operation, or authoring.
4. Successful recorded operations never become retry candidates because a setting, prompt version, source, or output file changed.
5. Work never attempted is not a failure. Queued work remains queued during strict retry.
6. A persisted budget/read blocker is distinguished from a failed model invocation. It may become runnable only after its obstacle is resolved.
7. Existing committed prompt files are protected in retry/recovery mode, including older successful versions and unverified or manually edited files. Refreshing such a prompt remains an ordinary-run action.
8. A saved valid result is recovered locally before considering inference. A failed file write must not require another model result.
9. Preview and execution use the same prepared selection. Consent does not authorize recomputing a broader candidate set.
10. Input drift, unsupported state, ambiguous output ownership, or a live writer causes a bounded refusal or exclusion, never a fallback to normal distillation.
11. Explicit overrides affect only selected unsuccessful operations. They cannot invalidate successes or repartition a saved clustering operation.
12. Successful digest values and their lineage remain unchanged when other digest keys are repaired. The containing JSON file may change to save those repaired keys.
13. Ratings, notes, annotations, preference reviews, and unknown preserved provenance fields survive artifact updates.
14. Dry run is read-only: no ledger creation, lock creation, scratch directory, automatic export, checkpoint migration, or runner invocation.
15. Repeating a retry after it succeeds makes zero model calls for those recovered operations.
16. The installed canonical and compatibility commands enforce the same rules.

This does not promise exactly-once provider billing. If the provider finishes but the process loses the response before it is durably saved, the local operation has an unknown outcome and may need another attempt. The guarantee is that recorded successful work and saved usable results are not deliberately called again.

**4. CLI contract and option interactions**

| Option | Meaning in this release |
| --- | --- |
| `--retry-failed` | Strict retry from the active recorded operation set. Does not infer failures from missing files. |
| `--retry-stage=all\|digest\|cluster\|author` | Narrows strict retry by operation kind. `cluster` includes recorded windows and merge operations. Requires `--retry-failed`. |
| `--recover-tasks=slug-a,slug-b` | Separate explicit recovery mode for named saved tasks. Authoring only. Mutually exclusive with `--retry-failed` and `--retry-stage`. |
| `--dry-run` | Print the complete local plan and exit without writes or subprocess-based runner preparation. |
| `--yes` | Accept the already displayed plan in scripts; does not enable other stages or optional follow-ups. |
| `--model`, `--runner` | Explicitly override attempt settings for selected operations only. Otherwise inherit recorded settings. |
| `--timeout` | Explicit seconds, passed through unscaled. Otherwise use the new timeout policy described below. |
| `--input-budget`, `--truncate` | Override selected-operation preparation only. Retain fixed source/task/window membership. |
| `--concurrency` | Limit selected operations in flight. Preserve the current default of 3. |
| `--no-breaker` | Preserve the existing explicit control over the systemic-failure breaker. |
| `--home` | Resolve the same existing data directory as all other commands. |
| `--no-follow-up` | Retain current behavior. |

Reject these combinations before any mutation or model invocation:

- Retry/recovery with `--fresh` or `--force`.
- Retry/recovery with explicitly supplied `--group` or `--no-group`.
- Retry/recovery with explicitly supplied `--project`, `--source`, or `--min-substance` in this release. Stage selection is the supported retry narrowing mechanism; named recovery is already an exact task selection.
- `--retry-stage` without `--retry-failed`, or an unknown stage value.
- An empty, malformed, duplicate-after-normalization, or unknown recovery task list. Explain the specific issue; do not partially execute a misspelled list.

Keep raw explicit options distinguishable from parser defaults and `flowArgs()` environment-derived defaults. The current parser defaults `group` to true; that must not falsely reject retries of a saved `--no-group` run. Ambient project/source/model settings must not silently alter retry identity. Recorded settings take precedence over ambient workflow defaults in strict mode; explicit CLI overrides remain visible in the plan.

Do not silently auto-select a different available runner if the recorded runner is unavailable. Report that preflight failure, or let the user supply `--runner`.

If selected operations used different recorded runners or models, show that breakdown. Construct only the required runners after consent and finalize each once its in-flight operations have joined.

**5. Defaults and timeout propagation**

Change `DEFAULT_TIMEOUT_MS` in `src/runners/shared.ts` from `300_000` to `900_000`. Update CLI help and current-default documentation. Preserve historical failure fixtures whose text deliberately describes a prior five-minute timeout.

The effective policy remains:

| Operation | Default timeout |
| --- | --- |
| Digest | 900 seconds per runner invocation |
| Author | 900 seconds per runner invocation |
| Cluster window | 900 seconds + 5 seconds per digest in that window |
| Cluster merge | 900 seconds + 5 seconds per combined task |
| Preference consolidation | 900 seconds + 5 seconds per preference |
| Any explicit `--timeout=N` | Exactly N seconds, without the automatic scaling |

The consolidation change is an inherited effect of the shared constant, even though consolidation is not part of strict distill retry. Test it and describe it accurately. This release does not add failed-consolidation recovery.

Record whether each attempt's timeout was explicit and its effective value. A retry inherits the most recent explicit timeout unless overridden. A recorded default follows the current default policy, so upgrading benefits old default-timed attempts. Show the effective timeout before execution.

More generally, settings precedence is: explicit options for this invocation, then the most recent recorded attempt on that operation, then its initial prepared settings, then current defaults. A second retry inherits an explicit model/budget/timeout override from the preceding failed retry instead of silently reverting. Retain explicit-versus-default provenance: inherited default timeouts follow the current timeout policy, while inherited explicit seconds remain exact. Budget and truncation inherit their most recent recorded effective settings unless explicitly overridden.

Keep `DEFAULT_INPUT_BUDGET = 400_000`, `MIN_INPUT_BUDGET`, and default `truncate=never`. Input budget is a content-character ceiling, not a model context guarantee. `600000` must remain an explicit user choice.

Raising the budget must not change a saved cluster window's membership. If a cluster request still exceeds an explicit lower budget, leave that operation blocked. Do not introduce a new cluster truncation algorithm under an existing flag.

**6. Durable operation store**

Add a versioned, owner-only operation store under the selected data home:

```text
distill/
  digests.json
  tasks.json
  operations.json
  operations/
    <operation-id>/
      input.json
      result.json
      publication.json
  writer.lock/
    owner.json
```

`operations.json` is the small active index. Larger immutable operation inputs and validated results live separately. The implementation may consolidate tiny files if justified, but it must preserve the identities, state transitions, and crash guarantees below.

Use existing private directory/file conventions: 0700 directories and 0600 files where supported. No secrets, environment dumps, or authentication material belong in these records.

Representative index model:

```ts
type OperationKind = "digest" | "cluster-window" | "cluster-merge" | "author";
type OperationState =
  | "queued"
  | "running"
  | "failed"
  | "blocked"
  | "result-saved"
  | "committed"
  | "skipped"
  | "superseded"
  | "resolved-by-fallback";

interface OperationRecord {
  id: string;
  revision: number;
  generation: string;
  runId: string;
  kind: OperationKind;
  unitId: string;
  state: OperationState;
  source: "normal-distill" | "explicit-task-recovery";
  logicalInputHash: string;
  promptVersion: number;
  schemaHash: string;
  dependencyIds: string[];
  inputPath: string;
  attempts: AttemptRecord[];
  resultHash?: string;
  publication?: PublicationReceipt;
  blockedReason?: string;
}
```

An attempt records its ID, owning run, start/end timestamps, runner/model, explicit versus default timeout, effective timeout, budget, truncation, prepared request hash, bounded attempt counts, outcome, and a bounded error classification/message.

Record output publication receipts using hashes and operation IDs. A successful artifact is not identified by slug or filesystem presence alone.

Identity rules:

- Generation and immutable logical inputs identify the work.
- A task slug alone is insufficient: title, rationale, membership, relevant digest content, and source evidence belong in its identity.
- A cluster window includes the exact original ordered session IDs and digest inputs.
- Model, runner, timeout, and budget are attempt settings for retry purposes.
- An intentional normal refresh creates a new operation revision and ID, even when its logical inputs match a previous successful operation and only the model or another cache setting changed. Never transition a committed operation back to running or failed. Retries append attempts to the selected unsuccessful revision instead.
- Normal cache lineage still records model/runner/prompt changes exactly as it does today.
- The ledger and the existing cache lineage serve different purposes; do not weaken normal cache checks to implement retry.

Use strict schema validation when loading the store. Reject unsupported future revisions, invalid IDs, path traversal, mismatched generations, dangling dependencies, and corrupt result hashes. Do not convert a corrupt ledger into an empty ledger and then start normal work.

The active index tracks current logical operations. A later normal run explicitly supersedes obsolete operations when it changes their inputs or replaces the grouping. Preserve the historical attempt record without selecting those superseded failures automatically. This release does not add a historical-run replay command.

`--fresh` in ordinary mode resets the active retry scope together with ordinary checkpoints after its existing consent gates. Archive its prior operation metadata/results under the old generation, or retain them as excluded superseded records. Never make them eligible in the new generation.

**7. What to capture before a call**

Prepare one immutable operation input bundle:

- Source export IDs, project/session/origin identity, exact content hashes, and lengths.
- Relevant outcome evidence and anaphora records, with hashes.
- The digest values actually supplied to authoring/clustering.
- The complete task definition or cluster window/merge input.
- Prompt/schema version identifiers.
- The original attempt settings and the planned output ownership guard.

Avoid duplicating the entire export corpus. Reconstruct source text from local exports only after checking its recorded hash. Store the smaller immutable metadata and digest/task snapshots needed to reconstruct the same operation. If source bytes have changed or disappeared, strict retry reports the operation as ineligible; it does not silently use newer text.

Persist queued operations before dispatch as they become known. For normal authoring, tasks become known after grouping. For clustering, persist the complete window partition before its first call.

For a known budget-blocked operation encountered within a consented run, persist the immutable logical input and blocker even though no runner call occurred. The normal command's whole-run budget refusal before consent remains read-only and creates no operation history; its guidance is to correct the budget and run normal distill again. Do not introduce a pre-consent write merely to make that refusal retryable.

An unreadable source whose original bytes were never fingerprinted cannot be called an exact retry after the file changes or appears; report that limitation and require normal preparation or explicit named recovery.

A failure that occurs before an operation can be prepared safely is a run-level error, not permission to infer an arbitrary retry request later.

**8. State transitions and recovery**

| State | Strict retry action |
| --- | --- |
| Queued, no attempt | Exclude; report as not attempted. |
| Running, owner still alive | Refuse concurrent execution. |
| Running, owner known dead, no valid result | Treat as interrupted and eligible after preflight. |
| Failed, unchanged logical input | Eligible after preflight. |
| Blocked, obstacle still present | Report blocker; zero calls for that operation. |
| Blocked, obstacle resolved | Eligible; label as previously blocked rather than a failed model response. |
| Result saved, artifact not committed | Repair locally using the saved result; zero inference calls. |
| Committed | Exclude, even if its output was subsequently edited or deleted. |
| Skipped | Exclude. |
| Superseded | Exclude. |
| Resolved by fallback | Exclude; preserve the historical failure for diagnosis. |

The normal write sequence is:

```text
prepare immutable input
  -> persist queued operation
  -> persist dispatch intent and owning attempt
  -> invoke bounded runner/validation process
  -> durably save validated result
  -> publish guarded output
  -> record committed result
```

On failure, persist the attempt outcome before returning it to the command's summary. On signal interruption, stop assigning new work and use existing runner cleanup. A hard kill is recovered by the persisted dispatch record and stale-owner check.

A saved result must be validated and hashed before publication. A response that fails schema or evidence validation remains a failed operation, not a publishable result.

Reconciliation must inspect the operation's result file before trusting its index state. A crash can occur after a valid result is durably written but before the index changes from `running` or gains `resultHash`. The result's operation/attempt ID, input identity, schema receipt, and content hash must allow detection of this case and zero-inference recovery. A stale index alone never proves that another call is needed.

For retries of cluster operations, `result-saved` is the successful end of inference. Leave adoption pending for a normal run, with no change to `tasks.json`.

**9. Atomicity, simultaneous runs, and human edits**

Create a common atomic private-write helper in `src/core/fsutil.ts` using a unique temporary file in the destination directory, file flush, close, rename, and directory flush where supported. Document platform-specific durability limits instead of claiming impossible guarantees.

Add one writer lock per data home for normal distill, strict retry, and explicit task recovery. This protects the operation store and existing fixed-path checkpoints against separate distill processes, not just concurrent workers inside one process.

Acquire the lock after consent and before mutation. Revalidate the preview's state fingerprint after acquiring it. A live owner prevents execution. Reclaim a stale lock only after verifying its recorded owner is no longer live, with ownership-token checks that prevent removing a replacement lock. An ambiguous owner is not automatically stolen.

Dry run reads lock status but never creates or clears a lock.

Digest commit:

- Save the validated result first.
- Read/merge the current digest checkpoint under the writer lock.
- Update only the selected digest and its corresponding lineage/invalidation entry.
- Preserve successful unrelated values.
- Record a publication receipt allowing restart reconciliation without inference.

Author commit:

- Save the validated author result first.
- Build Markdown and provenance into temporary files.
- Record their expected hashes and target ownership guards in a publication intent.
- Re-read current files and metadata immediately before commit.
- Preserve the latest annotations and unknown fields rather than overwriting the copy captured before a long model call.
- Publish the pair through a recoverable transaction. Two renames are not themselves a two-file atomic transaction; the intent and result must let the next run finish or recognize the partial commit.
- Mark the operation committed only after both target hashes match.

If the user edits a prompt while inference is running, retain that edit and the saved generated result. Report a publication conflict. A later retry may inspect/repair that conflict locally but must not purchase a second result.

Ordinary refresh can still replace an unedited generated prompt under its existing rules. Strict retry and named recovery do not replace an already committed prompt, even if a prior refresh attempt failed. Report such an item as requiring normal refresh. This deliberately favors the requested preservation guarantee.

Use the same source/output guard checks immediately before dispatch and publication. An export command or editor may change files without honoring the distill writer lock.

**10. Strict planner**

Implement a dedicated planner, rather than running the normal orchestrator with a few skip flags.

The planner:

1. Parses explicit retry options and rejects conflicts.
2. Resolves the data home without offering export.
3. Loads the active operation index and validates its schema/generation.
4. Filters by `--retry-stage`, never by a fresh corpus scan.
5. Classifies unsuccessful, interrupted, blocked, staged-result, successful, queued, and protected operations.
6. Reconstructs only candidate input bundles and checks source hashes.
7. Checks current output ownership and committed-success exclusions.
8. Applies explicit attempt overrides to candidates only.
9. Computes content limits without changing saved task/window membership.
10. Produces an immutable prepared plan and a stable plan fingerprint.

Prepare all selected inputs before dispatch. Authoring must use its saved input bundle; it must not reload a freshly repaired digest halfway through the retry and turn it into a new author request.

Require prompt/schema compatibility for unsuccessful operations as well as source identity. If the installed implementation cannot reproduce the recorded prompt version and schema, mark the operation ineligible and explain the mismatch. A new prompt must not be substituted for an old failed operation under strict retry. No cross-version prompt replay machinery is included in this release.

Suggested internal interface:

```ts
interface RetryPlan {
  mode: "retry-failed" | "recover-tasks";
  generation: string;
  fingerprint: string;
  modelOperations: PreparedOperation[];
  localRepairs: PreparedRepair[];
  excluded: OperationDisposition[];
  blocked: OperationDisposition[];
  settings: ResolvedAttemptSummary[];
}
```

A missing ledger in strict mode produces an actionable error with zero model calls:

```text
This run has no recorded failure history.
Strict retry cannot infer failures from missing output.
For specific saved tasks, use --recover-tasks=<slugs> --dry-run.
```

A valid ledger with no outstanding failures is a successful zero-call no-op. A malformed ledger is an error, not the same no-op.

**11. Preview, consent, execution, and counts**

Example preview; counts are illustrative:

```text
Strict retry — existing grouping stays unchanged

  1 failed digest operation
  0 clustering operations
  6 failed author operations
  1 previously blocked author operation, now within budget
  0 local repairs

Selected work: 8 operations
Effective author timeout: 900 seconds
Input budget: 600000 characters; truncation: never
Successful and unattempted work is excluded.

Existing bounded validation/transport retries may make additional
harness invocations for these same selected operations.

Proceed? [y/N]
```

List the actual selected IDs and dispositions in dry run, with concise failures and the effective model/runner per group. Show local artifact repairs separately from model work. Do not retain the old approximate “~94 authoring calls” presentation for strict mode.

Preserve the existing bounded corrective behavior for each selected operation:

- Digest evidence correction can make a second runner call.
- Cluster semantic correction can make a second runner call.
- Runner schema/parsing correction can make a second CLI attempt.
- Kiro's existing bounded empty-output backoff remains within the same operation.

Record those attempts against their owning operation. Do not describe logical-operation totals as exact provider requests, and do not add a new automatic network-retry policy in this release.

After consent:

1. Acquire the writer lock and revalidate the prepared plan.
2. Finish valid saved-result repairs without inference.
3. Resolve/preflight only the adapters needed for remaining model operations.
4. Dispatch only the prepared eligible operations with bounded concurrency.
5. Persist each attempt and outcome.
6. Apply the systemic-failure breaker to stop scheduling additional selected work when the environment repeatedly fails; let in-flight work checkpoint.
7. Finalize runner resources once each runner's operations have joined.
8. Release the writer lock and print a deterministic summary.

A changed plan is not silently recalculated under the old consent. Report the change and require a new invocation/preview. For a mixed eligible/blocked plan, execute only the disclosed eligible subset and return nonzero while selected blockers remain.

A repair-only plan uses a single local-write consent message and never constructs or preflights a runner. In a mixed plan, a runner availability failure must not prevent already authorized safe local repairs from completing; unresolved model work still causes a nonzero exit.

The breaker does not downgrade previously failed candidates to `queued`. Candidates it never reaches in this retry retain their earlier failed/interrupted status and remain retryable. Only operations with no previous attempt are genuinely queued and excluded.

Exit conventions:

| Exit | Meaning |
| --- | --- |
| `0` | All selected work completed, or a valid zero-work plan; well-formed dry run also returns 0 and reports blockers. |
| `1` | Invalid state/options, unresolved selected failure/blocker, publication conflict, missing history, or unsafe drift. |
| `2` | Consent declined, following the existing command convention. |
| Signal exit | Preserve conventional interruption behavior; next invocation can diagnose the recorded interrupted attempts. |

When there is nothing to call or repair, skip runner resolution entirely. A healthy zero-call retry should not require an installed model CLI.

**12. Clustering recovery without regrouping**

Persist the original partition and each window's response during ordinary clustering. Identify a window by immutable input membership and source digest hashes, not its current array position alone.

Required example:

```text
window 1: succeeded
window 2: failed
window 3: queued
merge: never attempted
```

Strict retry calls only window 2. It does not call window 1, window 3, merge, or author. It saves the recovered window response separately and leaves `tasks.json` byte-for-byte unchanged.

A failed single-window cluster behaves the same way: save its repaired response, and leave grouping adoption pending. This also applies when no `tasks.json` exists yet.

A merge is eligible only if that exact merge operation was already attempted and failed, with its combined-task input saved. Newly satisfied dependencies do not authorize inventing or calling a merge.

The current best-effort merge fallback needs a distinct terminal state. If a merge fails but a validated fallback grouping is committed, mark the merge `resolved-by-fallback`. Retain the error, but do not retry it later and change an already accepted grouping.

Give normal grouping publication a durable intent/receipt too. If the process dies after publishing fallback `tasks.json` but before marking its failed merge resolved, reconcile the file's grouping identity/hash against that receipt before selecting retries. A matching published fallback resolves the merge without inference. An unpublished or conflicting grouping intent is left for a normal run; strict reconciliation must never finish it by writing `tasks.json`.

On a subsequent **normal** `distill` invocation:

- Compare the saved operation inputs/settings against that normal run's requested lineage.
- Reuse matching successful/recovered window results.
- Run queued or changed work under the normal consent plan.
- Assemble/adopt the grouping and proceed to authoring only within that normal run.
- If the normal run changes the partition, model, prompt, or inputs, do not mislabel old results as matching cache entries.

Strict completion text:

```text
Recovered clustering result saved.
Existing task grouping is unchanged.
Normal distill can adopt matching recovered results and continue the pipeline.
```

**13. Recovery for the user's existing seven failed tasks**

Older runs have no operation ledger. Missing prompts do not prove a previous failure, and an existing old prompt does not prove that the most recent refresh succeeded.

Provide a separate explicit mode:

```sh
npx human-hindsight@1.8.4 distill \
  --recover-tasks=example-task-one,example-task-two \
  --runner=claude --model='claude-opus-5-5[1m]' \
  --input-budget=600000 --concurrency=3 --dry-run
```

Then repeat that exact selection without `--dry-run` to reach consent.

The real task names come from the user's final failure summary. Keep personal task names/transcripts out of public synthetic fixtures, release notes, and this reusable plan. Do not automatically run the user's seven tasks as part of implementation or publication.

Rules for the mode:

- Parse the entire explicit list and validate every slug before execution.
- Resolve only those slugs from the saved grouping. Never invent a task.
- Require valid source exports, saved digests, and a completed/partial member outcome.
- Inspect every requested task's existing output/provenance. Skip verified successful entries and protect existing unverified/manual content.
- Treat a known successfully authored but subsequently deleted output as prior success, not an automatic recovery target.
- Show each task as ready, already complete, protected, unavailable, or budget-blocked.
- Use an immutable snapshot of the saved task and its evidence.
- Record provenance as `explicit-task-recovery`; do not manufacture historical failure timestamps or claim the old tool recorded them.
- Perform authoring only: zero digest, cluster, merge, consolidation, or automatic export operations.
- Subsequent failures from this recovery attempt enter the normal strict retry ledger.

There is no previous author attempt from which to inherit legacy recovery settings. Prefer explicit CLI runner/model choices, otherwise use the saved grouping's recorded runner/model. If no runner identity is available, require an explicit `--runner`; do not silently choose a different installed harness. If the model is unspecified, display that the selected harness default will be used. Start with the current timeout policy, 400,000-character budget, `truncate=never`, and concurrency 3 unless explicitly overridden. Ambient workflow settings must not silently change this selection.

For the example 552,096-character task, 600,000 is enough for its reported member-content total. Recompute the actual total at execution; do not hard-code that old count or claim it guarantees provider acceptance.

The strict guarantee protects existing prompts even if that means a named task must be handled later through ordinary refresh. The preview must make this visible before the user spends.
